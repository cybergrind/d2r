# Level guidance framework: plan

Drafted 2026-09-30. Status: **phases 0–6 done 2026-09-30** (uncommitted); Phase 5 confirmations are listed in its
table (Black Marsh pending); Phase 7 (more levels) is next. Everything since the Win+C work started is uncommitted.

## Goal

Split the level work into a **generic framework** plus small **level handlers**:

- The framework owns memory reading, the Win+C dump, entry detection, polling, timing,
  logging, geometry, the preset table, schematic graphs and all OSD drawing.
- A handler owns only level knowledge: which areas it covers and which rooms are its points of
  interest. There is **one file per level (or level chain)** in `levels/handlers/`, written with
  shared helpers so a typical handler is a few declarative lines.
- Arcane Sanctuary becomes the first handler. There is no catch-all generic handler (decided with
  the user on 2026-09-30); game data is too irregular for one (see "Why no generic handler").
- Guidance is shown as an arrow card plus a **level map card**: the level's rooms, a dot for the
  player and dots for the points of interest.

## Standing rules (from this work so far; they apply to every step)

1. **Red/green TDD** ([development.md](../../development.md)). Write the failing test first,
   then the code, then refactor while green. Tests go under `tests/` mirroring module paths,
   use plain pytest functions and parametrization, and run via `uv run pytest tests -v`. Run
   `ruff format` and `ruff check` before delivery.
2. **Match targets by LvlPrest name pattern, never by a single Def.** Boss and stairs rooms exist
   once per doorway orientation. Arcane "Summoner N/S/E/W" are 525–528. Game 1 used 527 and
   game 2 used 525, and a fixed 527 silently missed the second game.
3. **A handler is confirmed only by a Win+C dump in that level.** Rules taken from lvlprest names
   alone are marked `confirmed=False`. Each confirming dump becomes a test fixture.
4. **No silent failures.** Guide or read problems are logged at WARNING once per distinct
   message, because DEBUG is filtered out of `probe.log`. A guided level whose target is not
   found is reported, and the guide retries.
5. **Never block the serve loop.** Polls take the capture lock with `acquire(blocking=False)`
   and skip when it is busy. Reads are bounded and read-only (`ResearchReader`). The process
   identity is checked after each read.
6. **Runtime never reads `third-parties/`.** The LvlPrest and level-name table is bundled data,
   regenerated by a build command pinned to the d2data commit from `third-parties/repos.json`.
7. **No seed decoding and no map generation.** Everything comes from Room2 data the client
   already holds (layout_notes.md "Level rooms"). The map seed hashes stay observed-only.
8. **Screen direction uses the isometric transform** (+x runs down-right, +y down-left). The
   compass word uses map axes (north = −y), which the user confirmed.
9. **Display behaviour:** show once per entry into a guided area, including re-entry after a
   town portal. The card lasts `level_guide_seconds` (5 s) and clears early when D2R loses
   focus. It shares the OSD with shop/identify/appraisal, and appraisal is suppressed while a
   guide is visible.
10. **Layout evidence lives in `layout_notes.md`.** Only offsets confirmed by dumps go into
    `native/layout.py`; MapAssist's ActMisc offsets are not confirmed on this build.
    Numbers are dated.
11. **Host/agent split.** The user runs `make serve` and presses Win+C on the host. The agent is
    sandboxed (it cannot see the game process) and works from `runs/level/*/level.json`,
    `runs/alt-d/*/probe.log` and fixtures.
12. **Every level-reading feature is a partial map reveal.** It carries the same ban-risk category
    as the OSD memory reads the user already accepted. Keep it passive: no input injection and no
    writes.
13. Do not commit unless asked. Other agents edit this tree concurrently (shop and runeword
    work, OSD direction cards), so leave their files alone and report their test failures
    separately.

### Handler files: declarative, one per level

A handler is data plus, rarely, a function. The helpers cover the known shapes:

```python
# levels/handlers/arcane_sanctuary.py
HANDLERS = [target('Arcane Sanctuary', areas={74}, label='Summoner', preset=r'Act 2 - Arcane Summoner [NSEW]')]

# levels/handlers/tower_cellar.py
HANDLERS = [
    stairs_down('Tower Cellar 1-4', areas={21, 22, 23, 24}, family='Act 1 - Crypt'),
    target('Tower Cellar 5', areas={25}, label='Countess', preset=r'Act 1 - Crypt Countess X'),
]

# levels/handlers/durance_of_hate.py  (LevelType says "Act 3 - Kurast"; rooms are "Act 3 - Mephisto")
HANDLERS = [
    stairs_down(
        'Durance of Hate 1-2', areas={100, 101}, family='Act 3 - Mephisto', extra=[waypoint('Act 3 - Mephisto')]
    )
]

# levels/handlers/halls.py  (the Temple family has no "Next" form)
HANDLERS = [
    target('Halls of Anguish/Pain', areas={122, 123}, label='Next level', preset=r'Act 5 - Temple (NE|NW|SW) Down')
]
```

- `target(...)`: one POI, the unique room whose LvlPrest name fully matches the pattern.
- `stairs_down(family)`: equivalent to `target(label='Next level', preset=rf'{family} Next [NSEW]')`.
- `waypoint(family)`: an optional extra POI (`{family} Waypoint …`), shown as a dot and a line.
- `combine(...)` / a custom `guide(snapshot)` function: only for levels with logic that doesn't
  fit a pattern.
- The registry discovers every module in `handlers/` and reads its `HANDLERS` list. Adding a
  level means adding a file; no central list is edited.

A handler's output is `Guidance(pois=[Poi(label, room, kind)], problems=[...])`. The framework
turns it into arrows, map dots and warnings. A POI whose pattern matches no room, or two rooms,
becomes a problem, not a guess.

### Why no generic handler (checked 2026-09-30 against d2data)

- A level's `LevelType` names its preset family for Tower Cellar ("Act 1 - Crypt"), Catacombs,
  the Halls ("Act 5 - Temple") and Worldstone Keep ("Act 5 - Baal"). It does **not** for
  Durance of Hate: the type is "Act 3 - Kurast" but the rooms are "Act 3 - Mephisto …".
- The last level of a chain (Tower Cellar 5, Catacombs 4) shares its family's `Next` presets in
  the data but never places one in the game.
- In the Cave and Ice families `… Down …` is a side cave, while in the Temple family it is the
  next level.
- Outdoor areas contain waypoint presets, so an automatic waypoint arrow would appear almost
  everywhere.

So each level states its family and targets explicitly; the helpers keep that to one line.

### How much each level needs verifying

Most of it is verified once or offline; nothing requires a manual Win+C per level.

| Layer | Verified by | How often |
| --- | --- | --- |
| Memory chain (unit → room → level → Room2 list, presets, bounds) | Win+C dumps | **once, done** (Arcane, 2026-09-30); **once more for outdoor levels** (Black Marsh) |
| Handler patterns | offline tests over the bundled table, generated from every handler: the pattern matches ≥1 name; all matches share the declared family; every area exists in the levels table | automatically, every test run |
| The target actually appears once in that level | **automatic evidence**: every entry into a guided area saves a compact snapshot (rooms, player, POIs found, problems) to `runs/levels/evidence/<area>/` | while playing; one sighting per **family** is enough, e.g. one Tower Cellar level covers all of 21–24 |
| Regression | `python -m inventory_tracking.levels.evidence fixture <file> <name>` turns evidence into a test fixture replayed by the handler test | once per family/handler |

The failure mode is safe. If a pattern doesn't match in the game, the guide logs a warning and
shows no arrow rather than a wrong one. A handler stays `confirmed=False` (shown, marked
unconfirmed in logs and evidence) until a fixture from the game backs it.

### Level map card

- **Data** (framework, every handled level): all Room2 bounds of the level, the player's world
  position and the POI room centres. `level_map.py` builds a `LevelMap` payload in map tiles:
  rooms, player, and POIs with label and kind.
- **Drawing** (`osd/level_map.py`, cairo): iso projection (screen x = x − y, screen y =
  (x + y) / 2), scaled to fit a fixed box. Rooms are low-alpha filled diamonds (a maze's room
  blocks show its shape); POIs are coloured dots with a short label; the player is a bright dot.
  It sits next to the arrow card and uses the same 5 s lease.
- **Live player dot:** while the card is visible, the guide re-reads only the player position on
  each poll (the cheap read, without the room list) and republishes, so the dot moves.
- **Limits:** the map has room-level granularity only. There are no walls, because Room2 carries
  no collision; loaded Room1s carry collision only near the player. Outdoor levels show as a
  large block of rooms, and there the dots carry the value.
- **Route (later):** preset names spell their doorways ("Crypt NSE"). A room graph (shared edge
  plus doorway letters on both sides) and a BFS from the player's room to the POI give a path
  highlighted on the same map. This is the "Tower schematic".
- **Display payload:** the OSD frame gains an optional `map` key next to `lines`. `osd/window.py`
  and `osd/direction.py` belong to another agent's in-progress work, so coordinate the payload
  change with it rather than editing around it.

### What stays generic (never in a handler)

Memory offsets and reads; entry detection, polling and the capture lock; warnings; evidence
capture and fixture export; the display lease and focus; iso and compass geometry; the preset
and doorway table; the map payload and drawing; the route graph; Win+C dumps; handler discovery
and validation.
