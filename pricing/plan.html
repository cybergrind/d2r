Contracts and boundaries

  • ItemObservation: image hash, full display name, candidate item/base IDs, raw OCR lines and boxes, per-field value/status/source, all modifiers, tooltip completeness and unresolved fields. Values have observed/reviewed/unknown/conflicting status. Null never means false or zero. Review overlay is separate from OCR and bound to image hash.
  • SearchRequest: intent, identity/base, quality, sockets, contents, ethereal, exact properties/minimums, class/build/variant, side and equip constraints. Property IDs resolved locally. Unknown OCR fields cannot become hard predicates. Broad discovery never silently relaxes the exact-comparable request.
  • EvidenceBundle: normalized item plus separate identity, exact comparisons, skill patterns, base/recipe rules, leveling/build/merc advice, vendor/keep rules, better-roll targets and current filter match. Every entry carries source ID/date/hash, match kind, prerequisites and applicability (met/unmet/unknown). Include counts/omissions and completeness for each branch.
  • Decision: action SELL/KEEP/VENDOR/REVIEW, price status and supported payable ask if any, trade value separate from utility, deciding fields and rule IDs, better-roll explanation, filter explanation, missing evidence and citations. No numerical price invented from absent data; VENDOR requires an applicable rejection rule plus completed keep checks.
  • Exhaustive tier coverage — required, pending implementation (2026-09-25): enumerate every unique item, every set and every set member in the scoped game definitions, including RotW additions. Every unique and every set piece needs a reviewed trade tier of high / med / low / trash plus an independent leveling assessment (high / med / low / none, with class, progression and conditions). Every set also needs overall usefulness and set-level leveling assessments. Low trade value must not hide leveling usefulness. No restriction to watchlists, build mentions or named examples. Completion requires zero missing/pending required records against the full census, with unique/set/piece coverage reported separately and exclusions explained. Missing evidence remains a blocking review gap, never automatic trash/none.
  • Set-item tiers — required, pending implementation (2026-09-25): every set item must report an overall set-use tier (full set and useful named combinations, build/mercenary use or reviewed lack of use), separate set-level leveling usefulness, and an independent individual-piece trade tier with its own uses, scarcity, roll conditions and leveling context. Do not copy the set tier or sibling prices onto all pieces. Preserve unknown/pending evidence separately from reviewed no-use. The user’s Immortal King armor example is an acceptance case: Soul Cage must retain its separately evidenced rarity/value premium over the other pieces. Exact tiers and prices require reviewed evidence; rarity alone is not a price. Coverage must account for sets, set-level leveling and pieces separately. See the implementation plan, §7–8 for the report and acceptance contract.
  • Combination-aware stat highlights — required, pending implementation (2026-09-25): bases, magic and rare items need a shared StatsEvaluator fed reviewed configurations with applicability, mandatory stat combinations, prioritized desirable/supporting stats and roll policies. Evaluate the whole item before assigning dots: green desirable, blue good/supporting, grey reviewed irrelevant/trash; unknown is neutral. Missing mandatory stats cannot be compensated by optional stats or combined across incompatible configurations. Keep dot desirability separate from good/bad roll text coloring, whole-item tiers and numerical prices. Source-backed ranges, thresholds and conditional roles govern both channels. See implementation plan §8.1 for evaluation order, configuration fields, rendering and acceptance cases.
  • Fast start without scope loss — planned (2026-09-25): complete the global base/item/use inventory first, reuse existing extraction and reviewed rules, deduplicate semantic configurations, and assign reviewed family templates with explicit exceptions. Deliver useful rule batches early; reserve regular batches for specialist/leveling/unresolved cases. Assessment configurations are intended here; in-game loot-filter profiles remain outside this update.
  • LLM role: interpret verified evidence and explain the decision; code owns typed matching, currency arithmetic, scope, prerequisite evaluation and response validation. Retrieved prose is evidence, not executable instructions. At most one bounded evidence expansion round initially; unresolved after that is a useful REVIEW result.
  • Offline definition: OCR, KB reads, missing-index recovery and price lookup never network. Initial deployment can use the existing assistant for visual review/reasoning with local tools; that is not fully local inference. A fully offline deployment requires an explicitly configured local vision/LLM runtime and its own accuracy/latency gate; no model or weights are silently downloaded.

The existing repo has 26 overall S/A builds, 71 runeword records and 62 recommended-base records.
