HTML planning documents — authoring guide

How we design, review and maintain planning documents in guides/*.html. Distilled from guides/ore-processing.html (the reference implementation) on 2026-08-09. This document follows its own rules — read it in a browser once, then use it as a template.

TL;DR — the model: one self-contained HTML file per topic, committed to git. The open text is for the human: TL;DR first, then the settled design, cheat-sheets and build phases. The collapsed <details> blocks are for agents: sources, working assumptions, rejected ideas, and a review log of every error already found and fixed — so a fresh clean-context agent is cut off from false paths before it starts. Every number obeys rule zero (verified with the tools, never from LLM memory; unverifiable claims flagged "verify in-game"). Reviews correct the text in place and append a log entry; the document is always the single current truth, never a discussion thread.

Preconditions & working assumptions
  • Rule zero (from AE2-PLANNING.md): LLM recall of GTNH facts is not evidence — every number in a planning document comes from the tools or is flagged "verify in-game". This guide's own factual claims are about the repo's documents and were verified by reading them (see the review log).
  • Two reader types, both first-class: humans render the file in a browser; agents read raw source and see collapsed content at zero cost.
  • Canonical stylesheet: the <style> block in THIS file. It contains every class this guide's advice requires (.legend/.dot, .prio, .vs, callouts, flows). ore-processing.html shares the palette but carries extra topic-specific classes (.lcr, .tag, .frag…) — add classes like those per topic as needed.
  • Documents are committed; generated reports are not. A planning doc quotes report numbers with their date instead of linking into reports/, which is reproducible and may be regenerated.
Rejected ideas (and why)
  1. Markdown for design documents. Kept for bootstrap notes and linear reference guides (AE2-PLANNING.md, BEES.md), but it lacks collapsed sections, fixed-meaning callouts and color-coded topology — the three features the dual audience needs most.
  2. One big per-tier document. Topics mature at different rates, and a review pass needs a bounded fact-set (~170 claims was one full fact-check); one topic per file keeps passes affordable and git history legible.
  3. A separate agent-notes file next to each human doc. Two files describing one design always drift; collapsed <details> keeps a single truth with two views.
  4. Vendoring mermaid into the repo. A ~1 MB asset per copy, or a shared asset path every document then depends on. The CDN plus the graceful-degradation rule costs nothing offline, because diagrams must have table twins anyway (§5.3). Revisit only if offline rendering becomes a real workflow.
  5. Inline revision markers in the body (strikethrough, "UPDATE:", editor's notes). The body must always read as the settled current truth; history belongs to the review log and git.

1 · Why HTML, and what a document is

A planning document is the settled state of a design, not a chat transcript. Markdown was fine for bootstrap notes (AE2-PLANNING.md), but for real designs HTML wins because it gives us, in one self-contained file (zero build step; the only optional runtime fetch is the mermaid CDN, which degrades to readable source, §5.3):

  • Two audiences in one file. A human skims rendered callouts and tables in a browser; an agent reads the raw source and sees everything — including the collapsed blocks that would only slow a human down. Collapsing costs the agent nothing.
  • Structure that survives editing. Stable keys (S0…S7 style), uniform per-stage templates, callout boxes with fixed meanings — an agent can patch one stage without reflowing a 3,000-word narrative.
  • Visual reasoning. Color-coded flow diagrams, priority ladders, comparison tables. In GTNH the topology is the design (which network owns which bus, what outranks what) — prose alone hides bugs that a diagram makes obvious.
  • Dark/light theming, print-friendly, zero build step. Open the file, read it. No server, no toolchain, works offline (diagrams degrade gracefully, §5.3).

One topic per file, lowercase-hyphenated name in guides/ (ore-processing.html, power-generation.html…). Git history is part of the record: commit after every meaningful revision with a message saying what changed and which review pass caused it.

2 · Anatomy — the canonical section order

Every document follows this skeleton. Sections marked ▸ collapsed are <details> blocks — agent payload, human-optional.

Header — <h1> + one .sub line: pack version, data source, date of last verification e.g. "every recipe verified against data-2.9.0-v7.bin (221,760 recipes) on 2026-08-08"
TL;DR box — the settled recommendation in one paragraph, bold on the load-bearing choices a returning human should be able to act after reading only this
▸ Links & sources — wiki pages, community guides, GitHub issues, repo tools collapsed; each link annotated with what it contributed
▸ Preconditions & working assumptions — rule zero restated, fork semantics relied on, what the base already runs, cross-plan context collapsed; this is the context a clean agent must load before touching anything
▸ Rejected ideas (and why) — every alternative considered and killed, with the killing argument collapsed; prevents re-litigation — see §4.2
▸ Review log — errors already found & fixed, per review pass, plus confirmed non-errors collapsed; cuts fresh agents off from false paths — see §4.1
agent preamble ends — human-facing body begins
The numbers — key quantities from the data, with their tool provenance
Concerns, point by point — the human's original doubts answered in a two-column table optional but valuable: it records why the design is shaped this way
The design — recommended layout, diagrams, walkthroughs of the non-obvious mechanics
The full detail ladder — every repeated unit under a uniform template with stable keys (§3.2)
Cheat-sheets — paste-ready strings, priority tables, exact configs with lengths/counts so limits are checkable at a glance
Variants compared · Build list — phases ("now" vs "later-tier polish"), rules of thumb
Appendix — ▸ raw data dumps · ▸ what is DB-verified vs verify-in-game (§4.3)
Footer — generation provenance: which tool scans, which sources, which baseline architecture

Not every document needs every section — a research-only doc has no build list — but never omit the TL;DR, the assumptions block, the review log (create it empty at draft time), and the verified-vs-not appendix.

3 · Writing for the two audiences

3.1 What collapses and what stays open

The rule: anything a human needs to decide or build stays open; anything an agent needs to not repeat mistakes collapses.

ContentWhereWhy
Settled recommendation, design, cheat-sheets, build phasesopen text the human's working surface
Sources, assumptions, fork semantics, plan context▸ collapsed, top an agent must load it; a human already knows it
Rejected ideas, review log▸ collapsed, top pure agent guard-rails — see §4
Raw data dumps (ore-processing's 86-pair table, closure inventories)▸ collapsed, appendix evidence, not reading material
Warnings a builder could physically get wrongopen .warnbox, at the point of usea collapsed warning is a missed warning

3.2 Repeated units: uniform template + stable keys

When the design has N instances of the same shape (processing stages, generator options, farm plots…), give each a stable key that is not a section number — S0…S7, G-benzene, P-passive-1 — and render each under the same field template. In ore-processing every stage is exactly In / Bus / Card / Out:

Inwhat arrives and from where
Busowner network, sticky, priority, target
Cardthe mandatory filter string, verbatim
Outwhat leaves and to which stage key

Pick the four-or-five fields that define a unit for your topic and never deviate. Why it matters: section numbers drift when sections are inserted (ore-processing carried stale §5.7→§5.8 references for a day); stable keys don't. And a uniform template lets an agent diff two units — or audit all of them — mechanically.

3.3 Atomic, checkable claims

  • Absolute dates, never "today"/"currently" — a document is read weeks later by an agent with a different clock.
  • Exact strings with counts: "43 ores, 681 chars — fits the 1024 limit" is checkable; "the list fits" is not.
  • Name the evidence inline: "source-verified in MTEBoxinator.java", "DB-verified 5 V recipe", "per wiki Ore Generation page". A claim without provenance is a claim the next review pass must re-derive.
  • One claim per sentence where it matters. Review passes fact-check ~170 claims at a time; compound sentences hide the one wrong half.

4 · The review discipline (the load-bearing part)

Documents at this depth are wrong in a dozen places on the first draft — ore-processing went through six review passes and every one found real errors. The process that makes this safe:

4.1 Clean-context reviews append to the review log — never to the body

Reviews are run by clean-context sub-agents: a fresh agent gets the file, rule zero, and the tool cookbook — no conversation history, so it can't inherit the author's blind spots. Its findings are handled in exactly two motions:

  1. The correction is applied in place. The body text always reads as if it had been right all along. No strikethrough, no "UPDATE:", no inline discussion.
  2. The error is recorded in the ▸ review log: what was wrong, what the truth is, what evidence settled it, dated per pass.
Why the log exists — false-path cutoff. A future clean-context agent, seeing only the corrected text, may independently re-derive the old wrong claim (it was plausible — that's why it got written the first time) and "fix" the document back to it. The log is the immunization: "this exact claim was believed, checked, and is wrong — here's the evidence — don't reintroduce it." The log also records confirmed non-errors: facts that look like typos but are verified correct (the crossed Stargatium rows), explicitly marked don't "fix" them. Both directions cut off a false path before an agent walks it.

Sub-agent review prompts should ask for different lenses on different passes: editorial/logic consistency, full fact-check of every claim against the recipe DB, source-level verification against the shipped jars, closure audit ("simulate every item this system can emit — does each one have a handler?"). Each lens catches a class the others miss.

4.2 Rejected ideas: kill alternatives permanently

Every alternative that was considered and dropped gets a numbered entry: the idea, and the specific killing argument (with numbers — "86 pairs → bus explosion", "only 2 input slots → permanent stall"). Purpose is the same cutoff: the obvious-looking alternative will occur to the next agent or the next human; the entry answers it in ten seconds instead of an afternoon of re-derivation. If a rejected idea has a narrow valid niche, say so in the entry ("kept only as a bridge for isolated single-ore crops").

Companion rule from AE2-PLANNING.md: settled decisions are listed and never silently re-litigated. Reopening one is allowed — but explicitly, with new evidence, and the entry gets updated either way.

4.3 Rule zero and the verified-vs-not appendix

Rule zero: LLM recall of GTNH facts is not evidence. Every recipe, quantity, voltage and behavior claim is verified against the tools — databin.py for recipes, craft_plan.py --explain for routes, quests.py / base_scan.py / player_report.py for world state (full cookbook in guides/AE2-PLANNING.md). Claims from the internet get double scrutiny: community guides are architecture inspiration, but their numbers are for other pack versions until re-verified against our DB.

What the tools cannot settle (GUI slot counts, in-world mechanics not in the recipe DB) is flagged "verify in-game" at the point of claim and collected in a closing appendix: ▸ What is DB-verified vs. verify-in-game. That appendix is the document's honesty ledger — a reader knows exactly which claims stand on evidence and which on convention.

Pack-version facts that keep tripping LLM memory (fuel maps, id traps, mechanics that changed since 2.7/2.8) are collected in guides/KB-GTNH29.md — consult it before web research, and feed newly verified cross-topic facts back into it.

4.4 State grounding — before asserting what the base has

The costliest failure mode observed so far is not a wrong recipe — it's a wrong "the base doesn't have X". A field-test draft asserted five major capabilities missing (petrochem fluids, an LCR, banked titanium, bees, automated chlorine) that all existed. Pack facts and base-state facts have different evidence rules; conflating them produces confidently wrong documents.
  • Two claim classes. Pack facts (recipes, fuel values, mechanics) come from the DB/jars/KB and stay true. Base-state facts (what is built, banked, automated, visited) are volatile — they require fresh scans, run during the writing session, cited with tool + date. Stale snapshots (even days old) are history, not state.
  • The scan battery: base_scan.py (item stacks incl. AE cells in drives), fluid_scan.py (fluid banks — tanks/hatches; items-only scans are blind to them), machine_scan.py (which machines/multiblocks are physically placed), player_report.py, quests.py. A "does the base have X?" claim needs the scan whose domain covers X — a missing-machine claim needs the machine census, a missing-fluid claim needs the fluid scan.
  • Quest state is progression evidence, never built-state evidence. Quests lag reality in both directions: unclaimed quests exist for things long built (banked Moon blocks with "Moon Arrival" unclaimed), and a completed quest doesn't mean the reward infrastructure exists. Cross-check against scans before any "not yet done" claim.
  • "Not found" ≠ "absent". The scanners publish honest gap sections; phrase negative findings as "not found by <tool> on <date> (<coverage caveat>)" and put them in the verify-in-game ledger, never as flat absence.
  • Cross-cutting topics are never silently omitted. If a sibling document owns a topic the reader would expect here (e.g. centralized power in a priorities doc), include the one-paragraph conclusion with a pointer — a reader of THIS document must not be able to miss it.

5 · Visual language

5.1 Callouts with fixed meanings

ClassMeaningRule
.tldrthe settled recommendationexactly one, at the top
.warnboxa mistake the reader could actually make at the point of use, never collapsed
.okboxa reassurance that closes a worry ("144 L = exactly one ingot — nothing to void")sparingly, or it becomes noise

Color-code entities consistently across the whole document (main network red, subnet blue, buffers amber, fluids teal, machines gray in ore-processing) and put a legend at the top if you use more than two colors. The palette lives in the shared stylesheet — reuse the CSS variables, don't invent new hex values.

5.2 CSS flows first, mermaid when the graph earns it

Two diagram tools, one decision rule:

  • .flow/.fbox CSS boxes (as in §2 above) for linear ladders and priority stacks. Zero dependencies, theme-aware for free, and each box holds rich HTML — filter strings, <small> annotations. This covers ~90% of GTNH planning diagrams because most of them are "things fall through a ladder" — ore-processing.html, 1,554 lines, is served entirely by these and contains zero mermaid.
  • Mermaid when the topology genuinely branches, merges or cycles — power distribution graphs, multi-path processing decisions, dependency DAGs between build phases. A CSS column can't show a diamond; mermaid can.

Embed once per document, in the <head>-equivalent position (snippet in the appendix skeleton). Live example — the document lifecycle:

5.3 Degrade gracefully

Mermaid loads from a CDN — offline, the <pre class="mermaid"> simply shows its source text, which is deliberately kept legible (short node labels, meaningful IDs). Never encode information only in a rendered diagram: the ladder a diagram shows must also exist as the stage tables. Diagrams are a view, tables are the truth. The same rule keeps the raw HTML readable for agents, who never render anything.

Handing off: a document following this guide needs no per-topic bootstrap file — the collapsed preamble (assumptions + rejected ideas + review log) is the topic handoff. A fresh agent needs exactly three things: the document, rule zero, and the shared tool cookbook (guides/AE2-PLANNING.md).

Checklist before calling a document stable
  • TL;DR alone is enough to act on — tested by reading only it.
  • All four preamble <details> blocks exist (sources, assumptions, rejected ideas, review log) and the log records every pass with dates.
  • Every number has provenance inline; every unverifiable claim says "verify in-game" and appears in the closing appendix.
  • Every "the base lacks / hasn't done X" claim cites a same-session scan (tool + date) whose domain covers X; quest state is never the sole evidence for built-state (§4.4).
  • Repeated units use stable keys + the uniform field template; cross-references to repeated units go by key, never by section number (top-level § references are fine — whole sections rarely move).
  • Warnings sit at their point of use in .warnbox, none collapsed.
  • Diagrams have a table twin; document is readable with JS off and in both themes.
  • At least two clean-context review passes with different lenses found nothing structural on their last run.
  • Committed, with the review passes visible in git history.
What is verified vs. judgment
  • Verified (review pass 1, 2026-08-09): every descriptive claim about ore-processing.html (structure, six-pass review history, the In/Bus/Card/Out template, string counts like "43 ores, 681 chars"), about AE2-PLANNING.md (rule zero, cookbook, the unsized-power open thread) and about README.md (document-before-apply workflow); tag-balance and entity-escaping of this file; the appendix skeleton containing §2's full never-omit subset; the five tools named in §4.3 existing in tools/.
  • Verify by opening the file in a browser: the mermaid diagram actually rendering (needs network for the CDN; unrendered it must still read as legible source — the §5.3 contract), and both color themes.
  • Judgment, not fact: the section order, the collapse rules, the two-lenses-minimum bar, and everything in Rejected ideas — conventions proven once (on ore-processing.html) and expected to generalize. Revise them through the review discipline, not silently.
